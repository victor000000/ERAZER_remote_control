# Release 1.0.2

SQX readiness now requires a complete generated-strategy count on its own
status line. Nonnegative whole counts with optional comma grouping are accepted.
An incomplete count keeps startup readiness pending until a valid status
arrives or the wait expires.

Offline unit tests cover truncated, fractional, malformed and multiline
counts. The [testing guide](../testing.md) covers the Windows PowerShell 5.1 and
PowerShell 7 matrix, Python documentation checks, 90% module coverage gate,
and synthetic fixtures. Use the [operations runbook](../safe-operations.md)
to verify live task and SQX state.

## Check a status reply offline

From the repository root in Windows PowerShell 5.1 or PowerShell 7, parse
two synthetic CLI replies. The first prints `4567`. The second prints `False`.

```powershell
$null = .\scripts\Initialize-Toolkit.ps1
$valid = "Status of project Example`nStrategies generated 4,567"
(ConvertFrom-SqxStatus -Content $valid).Generated
$partial = "Status of project Example`nStrategies generated 42 unfinished"
Test-SqxResponse -Content $partial -Kind Status
```

If a real start times out, the scheduled task may already have launched the
engine. Inspect that run using the [timeout recovery procedure](../troubleshooting.md#recover-after-a-headless-start-times-out).

## Verify and publish

1. Work from the existing publication repository and agree on one release
   owner. Keep operator overlays, credentials, licenses, strategy files, raw
   logs and backup receipts in the private workspace. Check the module version
   in the [manifest](../../src/ERAZER.RemoteControl/ERAZER.RemoteControl.psd1).
2. In the isolated release checkout, run `git fetch origin` and `git status --short --branch`.
   Review staged contents with `git diff --cached` and commit the intended source.
   Inspect `git diff origin/main...HEAD` and run `git diff --check origin/main...HEAD`.
   Confirm the checkout is clean so the test inputs match the candidate commit.
3. Run the [source, documentation and Windows checks](../testing.md#reproduce-the-checks)
   on that commit and record `git rev-parse HEAD`. The release owner pushes or
   merges the reviewed source once. If the destination advances first, integrate
   the new base and verify the resulting commit.
4. Confirm both Windows matrix jobs succeeded on the commit that reached
   the destination branch. Their run contains the NUnit results, coverage
   and diagnostics for that commit. Creating a tag or GitHub Release and
   activating a Windows bundle are separate operations.

For a published source regression, revert the affected change through the same
review and CI process. For an activated bundle, restore its previous version,
matching configuration and task definitions using [deployment recovery](../deployment-migration.md#3-approve-live-migration-separately).
